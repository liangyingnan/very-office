```
│   └── document_editor_service_worker.js
└── docs/构建计划-9.4.0离线版.md
```

**离线打开链路**（9.4 方案，与 9.3 的 sdk 内补丁方案不同，全部在宿主层完成）：

```
office.html ──(onlyoffice-config + openBuffer 字节)──▶ onlyoffice.html
onlyoffice.html 把 document.url 改写为 '_offline_'（触发 sdk 原生 OfflineApp，跳过协同 socket）
   → 空文档 onDocumentReady
   → x2t_helper.convertToBin(openBuffer → SER bin)   [x2t.wasm]
   → docEditor.openDocument({buffer: SER bin})        [OpenDocumentFromBin]
```

**离线保存链路**：

```
用户点保存 ──(onlyoffice-save)──▶ onlyoffice.html
   → frame.contentWindow.Asc.editor.asc_nativeGetFile3()   [取当前 SER bin]
   → x2t_helper.convertFromBin(bin → docx/xlsx/pptx/pdf)   [x2t.wasm]
   → postMessage(onlyoffice-saved, buffer) 回传给 office.html
```

**插件链路**：

```
api.js 收到 editorConfig.plugins.pluginsData（路径相对编辑器 iframe）
   → iframe 内 fetch(config.json) → 注册插件
   → 插件资源按 baseUrl（config.json 所在目录）加载
```

## 2. 关键原理（9.4 离线方案为什么这样设计）

### 2.1 为什么不能用 9.3 的 sdk 内补丁方案

9.3.0.136 的 `sdk-all-min.js` 里打了 `_downloadAsFromLocal` 等补丁（stub 掉协同与下载链路），
所以"感觉正常"。但 9.4 的 sdk 是**深度混淆的构建产物**，往里面打同样的补丁会
破坏运行（.record 记录过：TypeError 导致白屏卡死）。

9.4 的正确姿势（已在 onlyoffice-ai-word-demo 中验证通过）：

- sdk 自带 **OfflineApp 原生离线模式**：`document.url === '_offline_'` 时
  `DocInfo.put_OfflineApp(true)` → 协同 API 走 dummy 分支，**完全不创建 socket**（实测 0 请求）。
- 打开：`x2t.wasm` 把 docx/xlsx/pptx 字节转成 SER bin（`convertToBin`），再
  `docEditor.openDocument({buffer})` 注入（`checkStreamSignature('DOCY')` 通过 → `OpenDocumentFromBin`）。
- 保存：编辑器内核 `Asc.editor.asc_nativeGetFile3()` 取当前 SER bin（`{header, data}`），
  拼上 DOCY 签名后 `convertFromBin` 转回目标格式，字节直接 postMessage 回宿主。
- OfflineApp 启动需要三个 sdk 机关（word 已补 shim）：
  1. `AscCommon.getEmpty()` —— 空文档 SER bin（word 从 `sdk-all.js` 死变量 `g_sEmpty_bin` 现场提取）
  2. `window.compareVersions = true` —— 跳过"服务器版本过旧"守卫
  3. `_onEndPermissions` 许可包装 —— licenseResult 为 null 时补本地许可 `{type:3, rights:1}`
  4. `AscCommon.fetchFonts` —— x2t 转换时向 MEMFS 写字体（**当前缺失，见缺口 3**）

### 2.2 插件加载路径的坑

`web-apps/apps/common/main/lib/controller/Plugins.js` 的 `getPlugins()` 在**编辑器 iframe 内**
执行 `fetch(url)`，url 相对 iframe 页面解析。iframe 位于：

```
<root>/9.4.0/vendor/web-apps/apps/<editor>/main/index.html
```

所以 pluginsData 的正确相对路径是 `../../../../sdkjs-plugins/content/<name>/config.json`
（`main/` → 上 4 级 = `9.4.0/vendor/`）。当前配置里的 `9.4.0/sdkjs-plugins/...` 会拼到
`.../main/9.4.0/sdkjs-plugins/...` → 404。

插件资源的 baseUrl 由 `url.substring(0, lastIndexOf('config.json'))` 计算，插件 iframe
（index.html）同样相对编辑器页面解析，因此相对路径方案自洽。

### 阶段三：补齐 sdk 离线支撑 🔴

#### 3.1 实现 `AscCommon.fetchFonts`（必须）

x2t_helper.js 的 `fetchFonts()` 调用 `window.AscCommon.fetchFonts(cb)`，当前未定义 → 保存/导出必失败。

参考实现：OnlyofficePersonal 9.3 的 `word/sdk-all-min.js` 中 `AscCommon.fetchFonts`：
- 遍历 `AscCommon.g_font_loader.fontFiles`（含 NeedStyles/indexR/indexB 等字段）
- 从 `AscCommon.g_font_loader.fontFilesPath`（9.4 为 `"../../../../fonts/"`）XHR 拉取
- 用 16 字节 XOR 密钥 `[160,102,214,32,20,150,71,250,149,105,184,80,176,65,73,72]` 解密
- 回调返回 `[{fileName, binary}]`，x2t_helper 写入 `/working/fonts/`

落地方式（二选一）：
- **方案 A（推荐）**：写一个 `tools/inject-9.4.0-fetchFonts.py`，把 fetchFonts 实现以 IIFE
  增量追加进 word/cell/slide/visio 四个 `sdk-all-min.js`（参照现有 shim 的追加方式），
  并重建 `.br/.gz`。
- **方案 B（快速兜底）**：在 onlyoffice.html 里提前注入 `window.AscCommon.fetchFonts = cb => cb([])`。
  转换能跑通，但 PDF 导出字体不完整（record 遗留事项 #4 的已知限制）。

> 建议先 B 跑通全链路，再升级到 A 补真字体。

#### 3.2 cell / slide / visio 离线支持验证（🟠）

- **cell**：自带 `AscCommon.getEmpty`（调研已确认），理论上最接近可用。
  需补：compareVersions + 许可 shim + fetchFonts（同 word）。
- **slide / visio**：`sdk-all.js` 未见同款 `g_sEmpty_bin` 空文档 blob，需要验证
  OfflineApp 模式下 `_openEmptyDocument` 的行为，必要时从 word 提取空 bin 或
  用空白模板（blank.pptx）先 convertToBin 再 openDocument。
- 统一做法：把阶段三.1 的 shim 脚本做成参数化（`--product word|cell|slide|visio`），
  四个产品各跑一遍，逐一实测。

**验证点**：xlsx / pptx 新建、打开、保存全链路；PDF 打开/保存/导出。

   9.3.0.140 新编版仅作对照。

### 补充修复（2026-07-31 第五轮：保存/再打开越界）

**现象**：打开文档报 `Document conversion failed: RuntimeError: index out of bounds`。

**根因**：`asc_nativeGetFile3()` 返回的 `data` 是 **base64 字符串且已含 "DOCY;v10;0;" 文件头**
（`BinaryFileWriter.Write(true,true)` → `GetBase64Memory()`）。之前代码把 `header` 再拼接到
`data` 前面 → **双层 DOCY 头** → x2t 解析越界 → 保存产物损坏 → 再打开时 `memory access out of bounds`。

**修复**（Node 闭环实测验证）：
- `bin = atob(file3.data)`（base64 解码即为完整 bin，不再拼接 header；兼容字节数组类型）
- 闭环测试：打开(759) → 保存(PK 8410) → 再打开(DOCY 6085) ✅ 无越界
